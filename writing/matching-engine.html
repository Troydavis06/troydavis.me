What I learned building a matching engine from scratch

Feb 2026 · 6 min read

A matching engine is one of those things that sounds simple until you actually sit down to build one. At its core, it just matches buy and sell orders. Two sides of a book, some price/time priority logic, done. Except it’s not done, and the simplicity is a trap.

I built mine in C++ over a few weeks, mostly as a way to force myself to think seriously about data structure choices and concurrency. Here’s what stuck.

The order book is not a map

My first instinct was to use a std::map<double, vector<Order>> — price level as key, queue of orders as value. This works. It’s also wrong in ways that only show up under load.

Floating point as a map key is a footgun. Two prices that should be equal aren’t always, depending on how they got there. Exchanges use integer price representation (price in ticks) for exactly this reason. Once I switched to integer keys, a whole class of subtle bugs disappeared.

The other issue: iteration order. For a bid book you want descending price order, for an ask book ascending. std::map is ascending by default. You can use std::greater as a comparator, but it’s easy to get this wrong at the call site. I ended up wrapping both sides in a struct that made the iteration direction explicit.

Latency is about the hot path

Most of the time, the matching loop is idle. When it isn’t, it needs to be fast. The critical path is: receive order → check top of book → match or insert → emit fills. Everything else — logging, risk checks, persistence — needs to be off that path.

I got a decent speedup just by separating concerns aggressively. The match loop touches nothing it doesn’t have to. Side effects queue up and get processed by a separate thread. It’s a simple pattern but the discipline required to stick to it is underrated.

Concurrency is where it gets interesting

A single-threaded matching engine is fine for a toy. For anything real, you need to think about how orders arrive concurrently. I used a lock-free SPSC queue to feed orders into the engine from the gateway thread, which kept the matching loop off mutexes entirely. The engine itself is single-threaded by design — the book is owned by exactly one thread.

This is the same approach most real exchange engines use: serialize access through a single-threaded core, push concurrency to the edges. The alternative is fine-grained locking on the book, which is a great way to spend a week debugging deadlocks.

What I’d do differently

I underestimated how much of the work is in the protocol layer — parsing FIX or binary order messages efficiently, handling session state, dealing with reconnects. The matching logic ended up being maybe 20% of the total code. If I were starting over I’d scope that more honestly from the start.

I’d also add proper benchmarking earlier. I added it late and then had to refactor to make the hot path measurable. Measuring first would have shaped some early decisions differently.

Overall, building it was worth it. There’s something clarifying about working close to the metal on a problem with real performance constraints. Recommended if you want to get a feel for systems-level C++.
